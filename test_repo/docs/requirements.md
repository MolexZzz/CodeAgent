# 售货机项目需求文档

## 1. 项目目标

这是一个用于测试代码 Agent 的小型 Java 17 项目。当前仓库只提供领域模型、异常类型、库存容器和售货机类的空框架。第一阶段需要 Agent 根据本文档补全基础业务并编写测试；第二阶段在第一阶段完成后增加一个新功能并补充回归测试。

构建工具为 Maven，测试命令为：

```bash
mvn test
```

## 2. 现有代码结构

- `model/Product`：商品编码、名称和价格，价格单位为美分。
- `model/Coin`：5、10、25、100 美分四种硬币。
- `model/VendingMachineState`：`IDLE`、`PRODUCT_SELECTED`、`OUT_OF_SERVICE`。
- `service/Inventory`：保存商品和库存数量。
- `service/VendingMachine`：待实现的核心业务类。
- `exception`：已提供基础异常类型。

可以调整现有类的实现和公开方法，但不应删除需求要求的公共能力。可以增加小型辅助类。

## 3. 第一阶段：补全基础售货机

### 3.1 商品选择

实现 `selectProduct(String code)`：

1. 商品编码不存在时抛出 `InvalidProductException`。
2. 商品库存为 0 时抛出 `SoldOutException`。
3. 选择成功后记录当前商品，状态变为 `PRODUCT_SELECTED`。
4. 一次交易只能有一个当前商品；重新选择时应替换之前的选择。
5. 选择商品不应自动扣除库存或插入金额。

### 3.2 投币

实现 `insertCoin(Coin coin)`：

1. 非空硬币加入当前交易金额。
2. `insertedCents()` 返回所有已投入硬币的总美分数。
3. 尚未选择商品时也可以投币，金额应保留到后续选择。
4. 投币不应改变商品库存。

### 3.3 出货

实现 `dispense()`：

1. 没有选择商品时抛出 `InvalidProductException`。
2. 金额不足时抛出 `InsufficientFundsException`，并保留当前选择和投入金额，方便用户继续投币。
3. 金额足够时库存减少 1，返回找零硬币列表。
4. 找零金额等于 `insertedCents - priceCents`。
5. 找零必须使用贪心算法，优先返回面值较大的硬币，面值顺序为 100、25、10、5。
6. 出货成功后清空当前商品和投入金额，状态回到 `IDLE`。
7. 价格必须是非负整数；如果发现非法商品价格，可以抛出 `InvalidProductException`。
8. 当前库存、选择和金额的状态不能因为一次失败的出货被错误清空。

### 3.4 取消交易

实现 `cancel()`：

1. 返回当前投入金额对应的硬币列表。
2. 返回硬币应使用与找零相同的贪心顺序。
3. 取消后清空当前商品和投入金额，状态回到 `IDLE`。
4. 没有投入金额时返回空列表。

### 3.5 补货

实现 `restock(String code, int quantity)`：

1. 商品编码不存在时抛出 `InvalidProductException`。
2. `quantity` 必须大于 0，否则抛出 `IllegalArgumentException`。
3. 补货后库存数量增加。
4. 补货不应改变当前用户交易金额或当前选择。

### 3.6 库存和数据约束

1. 库存数量不能变为负数。
2. 对外返回的集合不应允许调用方绕过业务逻辑随意破坏内部状态。
3. `Product` 的编码、名称不能为空。
4. 业务代码应保持简单、可读，并使用已有异常类型。

## 4. 第一阶段测试要求

Agent 至少应新增测试覆盖：

- 选择不存在商品。
- 选择已售罄商品。
- 投入多枚硬币后金额正确。
- 未选择商品时投币金额仍保留。
- 金额不足时不能出货且交易状态保留。
- 正常出货会扣减库存并返回正确找零。
- 找零硬币顺序正确。
- 取消交易会退回金额并重置状态。
- 合法补货和非法补货。
- 商品和库存集合不会被外部调用者直接破坏。

不要为了让测试通过而删除或弱化测试。完成第一阶段后运行 `mvn test`，并在最终总结中说明修改的文件和测试结果。

## 5. 第二阶段：增加“精确付款”功能

第一阶段完成后，再提出以下新任务给 Agent：

> 在不破坏现有行为的前提下，增加精确付款模式：当机器无法为某个交易提供完整找零时，出货必须失败并保留交易状态；增加补充找零硬币后重试的能力，同时增加测试并运行完整回归测试。

第二阶段的业务约束：

1. 售货机新增能力，用于配置或启用“精确付款模式”。
2. 精确付款模式下，机器只能在能够提供完整找零时出货。
3. 如果没有足够的找零硬币，出货失败，库存、当前选择和投入金额都必须保持不变。
4. 普通模式可以继续使用第一阶段的贪心找零逻辑。
5. 设计应尽量保持向后兼容，不应破坏第一阶段已有的公共 API。
6. 可以增加 `restockChange(Coin coin, int quantity)` 或等价的公开能力，用于补充机器内部的找零硬币。
7. 新增测试必须覆盖：可找零成功、无法找零失败、补充找零硬币后重试成功、失败后取消交易、库存不被错误扣减。
8. “无法找零后继续投币”不是必需场景：由于找零金额等于投入金额减商品价格，继续投币只会增加找零金额，不能修复固定找零库存不足的问题。恢复路径应是补充找零硬币后重试，或者取消交易。

## 6. 验收标准

第一阶段和第二阶段都必须满足：

- `mvn test` 成功。
- 测试覆盖核心成功路径、失败路径和状态保持。
- Agent 的最终说明与实际 diff 一致。
- 不修改需求文档来规避需求。
- 不删除已有测试或通过降低断言强度来“修复”失败。
